# wtf-downloader Phase 1 技术选型与架构调研报告

- 项目代号：wtf-downloader
- 报告角色：首席架构师（高见远）
- 版本锚定基准日期：2026-10-23（所有版本号均经联网查证，来源为 crates.io / npm 官方或官方发布页）
- 结论适用范围：MVP 阶段（HTTP/HTTPS 直链多分片下载），V2（BT/磁力/视频解析）仅做架构预留

---

## 1. 调研范围与方法

本报告针对以下五组关键选型做对比与可行性验证，并为每条给出 ADR 草稿：

1. HTTP 客户端（reqwest / hyper / ureq）
2. 任务持久化（rusqlite / sqlx）
3. 全局限速（governor / 自实现令牌桶）
4. Tauri 2.x 版本与 Vue 3 集成方式（官方 create-tauri-app 模板）
5. 前端图标库（SVG 图标库锁定，全项目统一）

调研方法：查阅各候选的官方发布页与文档中的限制、MSRV、维护状态，不做"哪个更好"的泛泛比较；版本号一律锚定到具体补丁号，查证不到的标注"待验证"。

## 2. 选型对比矩阵与结论

### 2.1 HTTP 客户端（下载引擎核心依赖）

| 维度 | reqwest 0.13.5 | hyper 1.11.1 | ureq 3.4.2 |
|------|----------------|--------------|------------|
| 定位 | 高层异步 HTTP 客户端 | 底层 HTTP 实现（reqwest 的底座） | 简单阻塞式 HTTP 客户端 |
| 异步支持 | 原生 async（tokio） | 原生 async（需自建连接池/重定向等） | 仅阻塞 API，需自行开线程 |
| 流式响应体 | 支持 `bytes_stream()`，可直接对接分片写入 | 支持，但需手写 client 逻辑 | 支持，但阻塞模型不适合多分片并发 |
| Range 请求 | `RequestBuilder::header(RANGE, "bytes=start-end")`，官方文档明确支持 | 需手动构造 header | 支持 |
| TLS 默认 | 0.13 起默认 rustls（纯 Rust，Windows 免 OpenSSL） | 需自行集成 | rustls / native-tls 可选 |
| MSRV | 1.85.0 | 随 reqwest 满足 | 2.x 线 1.71，3.x 线以发布页为准 |
| 维护 | Sean McArthur（hyper 作者团队），约 1.26 亿次总下载 | 同一生态核心 | 活跃 |
| 学习成本 | 低（API 符合直觉） | 高（相当于自写半个客户端） | 低 |

**结论：选 reqwest 0.13.x。**

理由：
- 多分片并发下载是天然的多任务异步场景（N 个 Range 请求并行、每个任务一个 AbortHandle），reqwest 的 async Client + 连接池直接覆盖，零额外工作。
- ureq 阻塞模型在"每分片一个连接 + 全局共享限速 + 取消"场景下要自己管理线程池，复杂度反超。
- hyper 是 reqwest 的底层，直接用等于放弃连接池、重定向、超时等成品能力，违反"不过度设计也不做临时方案"。
- 版本注意：reqwest 0.13 将默认 TLS 切换为 rustls；若 MVP 需要兼容企业代理的 system-native TLS，可启用 `native-tls` feature（Windows/macOS 走系统 TLS，Linux 走 OpenSSL）。默认先用 rustls，遇到代理兼容问题再切。

### 2.2 任务持久化（SQLite 访问层）

| 维度 | rusqlite 0.40.2 | sqlx 0.9.0 |
|------|-----------------|------------|
| API 模型 | 同步、薄封装，直接暴露 SQLite 全部能力 | 异步、带连接池、编译期查询检查 |
| MSRV | 1.88.0 | **1.94.0** |
| 与 Tauri 2.12（MSRV 1.90）的兼容性 | 兼容 | **MSRV 高于 Tauri 2.12 的 1.90，同一 workspace 无法用同一工具链编译** |
| bundled SQLite | 支持（内置编译 SQLite 3.53.x，Windows 免系统依赖） | 走 libsqlite3-sys，同样可 bundled，但依赖面更大 |
| 单机单用户桌面场景契合度 | 高（下载器是单写者、低频写） | 其异步/多库能力在此场景无用武之地 |
| 集成方式 | 同步调用包 `tokio::task::spawn_blocking` 或专用写线程 | 原生 async command |

**结论：选 rusqlite 0.40.2 + `bundled` feature。** 这是本轮调研中最明确的一条：

1. **硬性冲突**：sqlx 0.9.0 的 MSRV 是 1.94，而 Tauri 2.12 的 MSRV 是 1.90。同一 cargo workspace 要求统一工具链，若锁 1.94 则要求所有开发者/CI 升级到尚未普及的工具链；若锁 1.90 则 sqlx 直接编译失败。rusqlite 0.40.2 的 MSRV 1.88 完全兼容。
2. 下载器的 DB 访问是"任务状态变更时写一行"，微秒级、低频，异步带来的收益为零，而 sqlx 引入连接池后台线程、宏编译期检查（需要 DATABASE_URL 或离线模式）等额外复杂度。
3. bundled 特性把 SQLite 编进二进制，Windows 安装包不依赖用户机器上的 sqlite3.dll——单文件分发 NFR 直接达成。

注意事项（写入 Spec 的硬约束）：
- rusqlite 是同步 API，在 Tauri async command 中必须经 `spawn_blocking` 或专用 DB 线程隔离，禁止在 async 上下文直接持锁查询（会阻塞 tokio runtime，Tauri 社区高频坑）。
- 打开连接后启用 WAL 模式（`PRAGMA journal_mode=WAL`），保证断电/崩溃时任务状态不损坏。

### 2.3 全局限速

| 维度 | governor 0.10.4 | 自实现令牌桶 |
|------|------------------|--------------|
| 算法 | GCRA（通用信元速率算法），无锁实现（单 AtomicU64 状态，CAS 更新） | 需自实现并自测 |
| 生态 | 92 万周下载，被 axum/tower 生态采用 | 无 |
| 动态调整速率 | 支持热调 rate（限速值运行时可变，对应"用户拖动限速滑杆立即生效"） | 需自己处理并发重建 |
| 批量取令牌 | `check_n` 支持一次取 N 个令牌（对应"按 chunk 批量限速"） | 需自己处理 |
| 跨任务共享 | `RateLimiter` 可包 `Arc` 共享，全部任务同享一个限速器 | 需自己处理 |

**结论：选 governor 0.10.4。**

- 全局限速的核心需求是"所有分片共享一个速率上限、速率可运行时调整"，governor 的共享 limiter + 热调 rate 精确命中，自实现大约 100-150 行还要自己扛并发正确性测试——这属于重复造轮子。
- 工程实践上按 chunk 粒度取令牌（如每 256KB 取一次），而不是按字节，避免限速器本身成为热点路径。
- 备选降级路径：若 GCRA 的离散速率表达在实际限速滑杆上不够平滑，可在 governor 之上包一层"目标速率 -> governor quota"的换算（约 20 行），仍优于全自研。

## 3. 核心功能技术可行性验证

### 3.1 进度事件推送（4Hz 节流）—— 可行，且有明确官方路径

Tauri 2 有两条 Rust -> JS 通信通道，官方文档与社区实践均给出明确选择依据：

| 通道 | 适用 | 本项目场景结论 |
|------|------|----------------|
| `emit` + `listen`（全局事件） | 广播给多窗口/多订阅者 | 任务列表全局刷新时使用 |
| `tauri::ipc::Channel<T>`（随 command 传入） | 单消费者、高频（>10/s）、有序流 | **进度推送主通道** |

官方/社区实测要点（写入 Spec 的硬约束）：
1. Channel 在 Rust 侧是**无界队列，无内建节流/背压**——进度事件必须在生产端（Rust）节流。4Hz（250ms 一帧）远低于 IPC 承受上限（社区建议高频不超过 ~60fps），技术上非常保守、安全。
2. 节流实现模式：下载引擎内部聚合各分片字节计数（覆盖写共享计数器），由定时器每 250ms 快照一次再 `send()`，即"coalesce + 定时发送"，而不是每读到 chunk 就发。
3. `Channel::send()` 返回 `Result`，Err 即 JS 侧句柄已释放（页面切换/组件卸载），应视为取消信号停止推送循环。
4. 全局事件（任务增删、状态机跳变）走 `emit`，低频场景，无性能顾虑。

### 3.2 系统托盘 —— 可行，核心能力无需插件

- Tauri 2 的托盘是**核心 feature**（`tauri = { features = ["tray-icon"] }`），不是插件。`TrayIconBuilder` + `Menu`/`MenuItem` 原生支持右键菜单、点击事件、tooltip。
- 典型行为链：点击托盘 -> 显示/隐藏主窗口（`window.show()/hide()`）、右键菜单含"退出"——MVP 所需全部覆盖。
- Windows 注意：托盘图标需要多分辨率 .ico 资源；关闭按钮 -> 隐藏到托盘而非退出（拦截 `WindowEvent::CloseRequested`）是社区标准做法。

### 3.3 开机自启动 / 单实例 —— 可行，官方插件覆盖

| 能力 | 方案 | 版本 |
|------|------|------|
| 单实例 | `tauri-plugin-single-instance`（Rust-only，无 npm 包） | 2.x（补丁号在 `cargo add` 时取最新，待验证具体补丁号） |
| 开机自启 | `tauri-plugin-autostart` | 2.x（同上） |

- single-instance 标准用法：二次启动时回调里聚焦已有主窗口，可透传命令行参数（V2 可用于"点击 .torrent 文件拉起应用"，MVP 仅做聚焦）。
- autostart 提供 enable/disable/isEnabled，设置页直接调用。
- 两者均为 desktop-only 插件，与本项目定位一致。

### 3.4 分片下载与断点续传 —— 可行，标准 HTTP 能力

- 断点续传依赖 HTTP Range（RFC 9110 `Range: bytes=start-end` + `206 Partial Content` + `Accept-Ranges` 响应头）。reqwest 官方文档支持任意 header 注入，分片请求即 `RequestBuilder::header(RANGE, format!("bytes={}-{}", start, end))`（以 reqwest 为例，示例，非指定）。
- `.part` 文件方案：每个分片写入 `目标名.part.NN`（或单 `.part` 文件按偏移 seek 写入，二选一，Spec 阶段定）；任务表记录每分片已完成字节数；恢复时对未完成分片重新发 Range 请求。
- 必须处理的边界（Spec 验收项）：
  - 服务器返回 200 而非 206（不支持 Range）-> 降级单连接顺序下载；
  - `Content-Length` 缺失（chunked 编码）-> 无总量进度，仅显示已下载字节；
  - 服务器 Range 与 .part 记录不一致（文件在服务端已变更，可用 ETag/Last-Modified 校验）-> 判定为失效，重下该分片或整个任务；
  - 30x 重定向后的最终 URL 才是分片请求目标。
- MVP 引擎 trait 抽象（V2 预留 BT/磁力）：引擎层定义统一任务模型与 `Downloader` 协议 trait（创建/暂停/恢复/取消/查询进度），HTTP 实现为第一个 backend；V2 的 BT 引擎实现同一 trait，桥接层与前端零改动。这是纯 Rust crate 内部抽象，不引入额外依赖。

### 3.5 重启恢复 —— 可行

- 任务与分片状态在 SQLite（WAL 模式）；应用启动时读取未完成任务，校验 .part 文件实际存在与大小，重新入队续传。
- 崩溃安全：WAL + 分片完成即更新 DB（低频写，性能无碍）。

### 4.2 分层依赖规则（硬约束）

1. `downloader-engine` **禁止**依赖 tauri/任何 UI 框架——这是"引擎可独立测试 + V2 可挂 BT"的前提。engine 对外只暴露纯 Rust API 与事件回调（`mpsc`/回调 trait），桥接层负责把回调转成 Tauri Channel/emit。
2. `app`（commands 层）是薄桥接：参数校验 + 调 engine + 结果序列化，**不写业务逻辑**；发现逻辑写到 commands 里即违规。
3. 前端 `api/` 层是唯一允许 import `@tauri-apps/api` 的地方，组件不直接 invoke——保证 V2 若换通信方式只改一层。
4. 单文件 <= 300 行、单一职责、入口文件只装配不写逻辑；Rust 侧按资源/能力分包（protocol/http/store/task），不按层横切。
5. UI 技术栈（以官方模板为例，示例，非指定）：Vite + Vue 3 + TS；路由 `createWebHashHistory`（WebView 非 HTTP 服务器，hash 路由是桌面应用标准做法）。

## 5. ADR 草稿（MADR 格式）

### ADR-001: 使用 reqwest 0.13.x 作为下载引擎 HTTP 客户端

- **Status**: Accepted (2026-10-23)
- **Background**: 多分片并发下载需要：异步并发连接、Range 请求、流式响应体、连接复用、可配置 TLS。候选 reqwest 0.13.5 / hyper 1.11.1 / ureq 3.4.2。
- **Decision**: 选 reqwest 0.13.5。hyper 需自建连接池与重定向（过度设计）；ureq 为阻塞模型，与"多分片并发 + 异步取消"模型冲突。默认 rustls TLS，保留 `native-tls` feature 作为代理兼容降级开关。
- **Consequences**: 正面——API 成熟、MSRV 1.85 兼容 workspace 工具链 1.90、社区案例最多。负面——0.13 默认 TLS 为 rustls，个别企业代理环境可能需要切 native-tls（已留降级路径）。
- **Related ADRs**: ADR-003, ADR-004

### ADR-002: 使用 rusqlite 0.40.2（bundled）作为任务持久化

- **Status**: Accepted (2026-10-23)
- **Background**: 需要单机嵌入式 DB 存任务/分片状态，重启恢复。候选 rusqlite 0.40.2 / sqlx 0.9.0。
- **Decision**: 选 rusqlite 0.40.2 + bundled。决定性因素：sqlx 0.9.0 MSRV 1.94 高于 Tauri 2.12 的 MSRV 1.90，同 workspace 无法用统一工具链编译；且桌面单写者场景不需要异步连接池。bundled 编译内置 SQLite 3.53.x，Windows 分发零系统依赖。启用 WAL 模式。同步调用一律经 `spawn_blocking` 隔离。
- **Consequences**: 正面——零 MSRV 冲突、依赖面最小、bundled 免 DLL 地狱。负面——查询无编译期检查（以测试覆盖补偿）；需自律处理 async 边界。
- **Related ADRs**: ADR-004

### ADR-003: 使用 governor 0.10.4 实现全局限速

- **Status**: Accepted (2026-10-23)
- **Background**: 需要跨任务/跨分片共享的全局速率上限，且限速值运行时可调。候选 governor 0.10.4 / 自实现令牌桶。
- **Decision**: 选 governor 0.10.4（GCRA 算法，无锁 AtomicU64 状态）。按 chunk 粒度（如 256KB）批量取令牌，避免限速器成为热点。共享 limiter 以 `Arc` 注入每个分片任务。
- **Consequences**: 正面——无锁高性能、支持热调速率与批量令牌、生态验证充分。负面——GCRA 的速率表达是离散 quota，若滑杆场景不平滑需加一层换算（约 20 行）。
- **Related ADRs**: ADR-001

### ADR-004: Tauri 2.12.x + Vue 3.5 + Channel 进度推送

- **Status**: Accepted (2026-10-23)
- **Background**: 跨平台桌面客户端，Windows 优先。需托盘、单实例、自启动、高频进度推送。用户指定 Vue 3 + TS 前端。
- **Decision**: 锚定 tauri 2.12.2+（含 2.12.2 的 macOS restart 修复与 2.12.3 的 Channel 修复）、@tauri-apps/api 2.12.x、CLI 2.12.2。脚手架用官方 `create-tauri-app --template vue-ts`（Vue 3.5.44 / Vite 8.3.x）。进度推送走 `tauri::ipc::Channel`，生产端（Rust）250ms 节流（4Hz）；任务级增删/状态变更走全局 `emit`。托盘用核心 `tray-icon` feature；单实例 `tauri-plugin-single-instance` 2.x；自启动 `tauri-plugin-autostart` 2.x。
- **Consequences**: 正面——Channel 是官方为单消费者高频流设计的通道，4Hz 远低于 IPC 上限，性能余量大；官方模板保证 Vue/TS/Vite 版本组合经过验证。负面——Tauri 2.12 放弃 Windows 7（对本项目无影响）；Channel 无界队列要求节流纪律必须在引擎侧强制执行（写入 Spec 硬约束）。
- **Related ADRs**: ADR-001, ADR-002, ADR-005

### ADR-005: 锁定 @lucide/vue 作为唯一前端图标库

- **Status**: Accepted (2026-10-23)
- **Background**: P0 规则要求全项目统一一套 SVG 图标库。候选 @lucide/vue（Lucide v1.61.0）/ Tabler / Phosphor。
- **Decision**: 选 @lucide/vue。线性风格一致性最严格、1900+ 图标覆盖工具类 UI、官方维护 Vue 3 组件包、tree-shakable。**禁止安装已废弃的 lucide-vue-next（2026-03 起 deprecated）**；全项目不得混入其他图标来源。
- **Consequences**: 正面——一套风格贯穿、按需打包体积小。负面——若需要极特殊的品牌/文件类型图标需以自绘 SVG 补充（同样纳入统一 stroke 规范），不得引入第二套图标库。
- **Related ADRs**: ADR-004

## 6. 技术约束与不可行警告

### 6.1 硬约束（违反即返工）

1. **Rust 工具链统一 1.90+**（Tauri 2.12 MSRV）。CI 与所有开发者 rustup 版本下限写入 README。
2. **sqlx 禁用**：MSRV 1.94 与 Tauri 2.12 冲突，任何成员不得引入。
3. **rusqlite 同步调用必须 spawn_blocking 隔离**，禁止在 async command 中直接持 Connection 查询。
4. **SQLite 必须 WAL 模式**。
5. **进度推送节流在 Rust 生产端实现**（250ms），禁止前端节流兜底（Channel 无界队列会在前端节流时积压内存）。
6. **downloader-engine 零 Tauri 依赖**。
7. **图标库唯一：@lucide/vue**；lucide-vue-next 为废弃包，禁止使用。
8. **文档/界面禁止 emoji 图标；禁止紫色到粉色渐变视觉方案**（P0 规则）。
9. Windows 目标为 Win10/Win11（WebView2）；Win7 不在支持范围。

### 6.2 不可行/风险警告

| 等级 | 项 | 说明 |
|------|----|------|
| 阻断级（已规避） | sqlx 0.9.0 与 Tauri 2.12 工具链冲突 | 已通过选 rusqlite 规避，列为禁用项防止后续引入 |
| 高 | 服务器不支持 Range（返回 200） | 部分直链/CDN 不支持分片；必须实现单连接降级路径，否则该类任务直接失败 |
| 高 | 资源在服务端变更导致续传错乱 | 用 ETag/Last-Modified 校验，不一致时判定 .part 失效重下；不做校验会产生静默数据损坏（最贵的一类故障） |
| 中 | rustls 与企业代理兼容性 | 留 `native-tls` feature 降级开关 |
| 中 | Tauri 插件补丁版本漂移 | single-instance/autostart 锚定 2.x 主线，具体补丁号在脚手架落地时 `cargo add` 锁定并回填本报告 |
| 低 | Vite 8 / TypeScript 7.x 新工具链偶发兼容问题 | 官方 vue-ts 模板生成的组合已验证可用；锁模板生成时的实际版本即可 |

### 6.3 待验证清单（脚手架落地时回填）

- [ ] WebView2 在目标 Win10 机器的预装情况（安装器需内置 WebView2 bootstrapper）

## 9. 端到端验证步骤（本调研结论的验收方式）

1. `npm create tauri-app@latest -- --template vue-ts` 生成骨架，确认 Vue/Vite/TS 版本与本报告 2.4 节一致，回填补丁号。
2. 在 workspace 中建立 `downloader-engine` 空 crate，`cargo test` 独立运行通过（证明零 Tauri 依赖）。
3. 引擎内用 reqwest 对公网测试直链（如大文件镜像）发起 2 分片 Range 下载，中途 kill 进程，重启后从 .part 续传完成，校验最终文件哈希与源一致。
4. governor 全局限速设 1MB/s，同时跑 2 个任务 4 分片，观察合计速率稳定在 1MB/s 附近。
5. Tauri app 挂托盘 + single-instance + autostart，双击二进制两次仅出现一个窗口并聚焦；关闭主窗口缩到托盘。
6. 前端以 4Hz 收到 Channel 进度且 UI 无卡顿；切换页面后 Channel send 返回 Err 且下载不中断（引擎与推送解耦）。

以上 6 步全绿，方视为 Phase 1 选型结论得到实证，进入 Phase 2 Spec。

## 10. 设计联动确认（2026-10-23 追加，回应设计侧移交的三个确认点）

### 10.1 自定义标题栏与 Win11 Mica 材质 —— MVP 采用原生标题栏，Mica 作为预留增强项

- **MVP 决策：使用原生系统标题栏（默认 decorations），不启用 Mica。** 理由：自定义标题栏需要自行实现拖拽区、最小化/最大化/关闭按钮、双击标题栏最大化、Win11 Snap Layouts 交互等（约 0.5-1 周成本），对一个下载器工具属于装饰性投入，违反"不做过度设计"。
- **预留路径（设计侧照此准备 token）**：`--bg` 定义为不透明色；同时预留 `--bg-translucent`（如 rgba 近黑 0.62 一类的半透明叠加版本），后续若启用 Mica 无需重新设计。
- 技术事实（已查证）：Tauri 2 通过 `tauri.conf.json` 的 `windowEffects.effects: ["mica"]` 支持 Win11 Mica，前提是 `transparent: true` 且 html/body CSS 背景透明、内容由半透明叠加层承载；Win10 无 Mica，需按 acrylic -> 不透明降级链处理；Linux 无系统级材质 API。届时启用是纯增量改动。

### 10.2 字体离线子集内嵌 —— 批准，附权重与体积约束

- 方案确认：woff2 子集 + `unicode-range` 分片声明，随 Tauri 打包内嵌（custom protocol 本地加载，完全离线），无任何运行时字体下载。
- 约束（写入 Spec，2026-10-23 与设计侧对齐后细化）：字重资源收敛为 5 个——Inter 400/500、Noto Sans SC 400/500、JetBrains Mono 400（设计侧已确认原 600 字重场合改用 500 + 字号区分，不再引入 600）；"5 个"指字重维度，Noto Sans SC 按 unicode-range 拆分后的物理文件数不在此限，但总体积目标 <= 3MB 不变；CSS 中保留系统字体回退栈（加载失败不白屏）。
- 理由：Noto Sans SC 单字重全量数 MB，不子集化会把安装包撑大一个数量级；Tauri 资产内嵌后离线可用性天然满足。

### 10.3 托盘 tooltip 实时刷新 —— Windows 可行，定位为低频辅助通道

- 技术事实（已查证官方 API 文档）：`TrayIcon::set_tooltip` 在 Windows 支持运行时更新；Linux（AppIndicator 协议）不支持 tooltip；macOS 支持。另 `set_title`（数值型托盘角标）仅 macOS 可用，Windows 不支持。
- 工程决策：tooltip 定位为**低频辅助显示**，不作为实时速度的主通道——tooltip 仅在鼠标悬停时可见，实时性价值有限。刷新频率约束 1Hz，仅在存在活动任务时更新；内容格式如"wtf-downloader — 3 个任务下载中 1.2 MB/s"（以产品文案为准，示例，非指定）。总速度的主展示位在应用内任务页/托盘菜单项文本，二者无平台限制。
- 桥接层注意：tooltip 更新与 4Hz 进度推送共用 Rust 侧聚合定时器数据源，但独立节流（1Hz），互不干扰。
